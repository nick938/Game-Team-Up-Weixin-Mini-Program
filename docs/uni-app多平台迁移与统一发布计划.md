## 1. 目标、范围与决策

目标是用一套主要业务源码服务微信及更多小程序平台，共用大厅、队伍、用户权限和运营后台，并用同一套流水线管理各端版本。优先保证现有微信用户、历史队伍和分享链接可继续使用。

| 决策 | 计划 | 生效条件 |
| --- | --- | --- |
| 前端基础 | 普通版 uni-app + Vue 3 + TypeScript | 首轮多端兼容验证通过后锁定依赖 |
| 工程起点 | unibest，裁剪演示页和非必要插件 | 核查模板许可证、依赖和生成代码；不直接覆盖现有工程 |
| UI | 优先评估 Wot UI；uni-ui 作为基础组件候选 | 按目标端验证所需组件，不能以框架支持代替组件验收 |
| 状态与请求 | Pinia + 基于 uni.request 的统一 API 客户端 | 不同时引入多个请求状态库；人数和队伍状态不使用长期本地缓存 |
| 后端 | 优先保留腾讯云现有数据资源，增加 HTTPS API 和统一鉴权 | 先验证当前微信云开发环境的 HTTP、服务端访问、套餐与域名能力 |
| 身份 | 内部 userId + 分平台登录身份映射 | 后端校验平台登录凭证，客户端不能指定可信身份 |
| 发布 | GitHub Actions 按平台构建和上传 | 仓库 Actions 可用，账号具备工具权限和上传凭据 |
| 上线顺序 | 微信回归 + QQ 接入验证优先；再扩展抖音、支付宝等 | QQ 具体路线及其他平台准入逐项确认，不承诺所有平台均可上架 |

本文件最初作为规划交付，现已按用户指令开始 P0，隔离原型位于 `experiments/p0-uniapp/`。实施期不顺带重做视觉风格，不新增聊天、语音、支付、推荐算法，不以迁移为由改变房间密码权限、表单必填项和现有订阅规则。H5 可作为开发与演示端，不替代小程序真机验收。

## 3. 平台推进策略与 QQ 专项

2026-10-16 用户明确：本分支目标为文档技术栈的 uni-app 迁移，并在**独立 QQ 小程序**正常使用。当前尚无 QQ 账号/AppID，先推进本地迁移和适配；不把 QQ 内运行微信小程序作为该目标的替代验收。以下两条路线保留为历史调查背景：

1. QQ 内运行当前微信小程序：先确认 AppID 的接入资格、宿主识别、登录和 wx.cloud 支持情况。不能以“没有 QQ 插件”直接认定截图原因，也不能默认需要额外 QQ 安装包。
2. 独立 QQ 小程序：只有账号可注册/发布且官方仍支持该路线时，才建立 mp-qq 构建与上传任务；确认其登录和云资源限制。

两条路线采用不同的构建/发布定义。若 QQ 复用微信产物，发布台账记录宿主验收结果，不伪造独立 QQ 包。若当前资格不满足，标记该端受平台条件阻塞，继续微信迁移和其他已满足条件的端，不靠换框架绕过平台限制。

| 批次 | 目标端 | 首批验证范围 |
| --- | --- | --- |
| A | 微信 + QQ 接入原型 | 登录、读取同一大厅、详情、头像、上车与车头权限 |
| B | 抖音、支付宝 | 同一后端核心闭环，独立处理授权、分享、内容检测和消息 |
| C | 百度、快手、小红书、京东等候选端 | 先核查准入、组件与上传工具；按可达用户和维护成本选取 |
| 按需 | 飞书、钉钉、淘宝等 | 只有存在明确入口和使用场景才增加适配 |

## 4. 前端工程与页面迁移

### 4.1 目录建议

以下是实施目标；当前已创建 apps/miniapp 前端并迁入 10 个页面，其余目录和后端改造仍须按实际代码核对。保留原工程直到新版微信完成验收和稳定观察。

```text
miniprogram/                  # 原生微信兼容版本
cloudfunctions/team/          # 原云函数入口，过渡期保留
apps/miniapp/                 # uni-app 新前端
  src/pages/                  # 保留现有页面路径语义
  src/components/             # 业务卡片、资料填写、统一空态
  src/api/                    # 登录、队伍、用户、管理 API
  src/stores/                 # 会话、资料、必要页面状态
  src/platform/               # 登录、分享、订阅、上传、宿主能力
  src/utils/                  # 格式化、校验、游戏目录、入口解析
packages/contracts/           # DTO、错误码与校验规则；不包含服务端密钥
server/                       # 可被旧云入口和 HTTP 入口调用的业务层
scripts/migrations/           # 身份映射、回填、核对与恢复脚本
scripts/release/               # 构建及各端上传适配
docs/                         # 接口、迁移记录、验收及发布台账
```

先验证旧云函数打包能包含共享业务层，再确定复用实现。不能让旧入口引用未随部署上传的仓库外文件。第一阶段只拆必要模块，避免一次改写整个大云函数。

### 4.2 迁移次序与行为清单

| 批次 | 页面/组件 | 必须保持的行为 |
| --- | --- | --- |
| 1 | 卡片、格式化、游戏目录、大厅、游戏落地页 | 默认排序、分页、搜索范围、详情 ID 和状态一致 |
| 2 | 资料填写、我的、登录会话、头像 | 资料要求、我发起/我加入、进行中/历史、数量与头像可见性 |
| 3 | 详情、发车、编辑、再发一趟 | 服务端校验、时间边界、并发上车、密码访问和车头管理 |
| 4 | 协议、反馈、报错、举报、欢迎信 | 原入口、错误预填、举报去重和内容检测 |
| 5 | 管理端、组局员代开 | 管理鉴权、封禁、代开目标验证和审计 |
| 6 | 微信分享、朋友圈单页、订阅消息 | 保持微信体验；其他端按实际能力提供对应交互 |

公共模块通过 platform adapter 调用宿主能力。页面不散布大量 wx/qq/tt/my 判断。能力配置至少包含宿主、登录方式、聊天分享、朋友圈、订阅、文件上传、客服/联系入口；不支持的操作给出可理解的说明，不能点击后无反应。

保留 `pages/team/detail?id=...`、游戏落地参数与历史入口解析。uni-app 编译后的真实路径须与原路径逐一比对；路径发生变化时保留兼容落地页。微信分享卡片不能假设可被抖音或支付宝直接识别。

现有订阅拒绝不能阻断发车/上车；资料填写不冒充平台授权。QQ、抖音和支付宝的昵称、头像、隐私授权单独验收。

### 4.3 工程选型验证

- 锁定一组能同时工作的 uni-app、Vue、TypeScript、Vite、unibest 和 UI 版本，提交 lockfile；不分别盲目升级到最新。
- 验证按钮、输入框、日期时间选择、表单错误、弹窗、上传、长列表、下拉刷新、tabBar 和安全区；组件通过编译后还要真机操作。
- 保留原视觉资产与交互布局，业务卡片自主封装；引入组件库不意味着重做 UI。
- UnoCSS 使用小程序兼容预设；运行时拼接类需处理构建扫描，避免某端样式缺失。
- 首期只安装实际需要的路由、组件导入、状态和请求依赖；不同时叠加多个路由/请求方案。

## 5. 后端统一方案

### 5.1 默认路线与备选

首选“保留现有数据 + 可验证的 HTTP 接入 + 共用业务层”。先在测试环境验证一次真实的跨端登录、授权读取和写入，再决定是否扩大迁移。

| 路线 | 采用条件 | 附加工作 |
| --- | --- | --- |
| A：原环境复用 | 当前环境支持合适的 HTTP/服务端入口且成本合理 | 增加网关、鉴权、参数解析和用户映射 |
| B：独立 CloudBase / 云托管 | A 不满足，且测试证明可安全承接现有资源或迁移数据 | 独立环境、服务端凭据、数据复制/切换和费用核对 |
| C：uniCloud 或自建 API | 团队明确选择其生态，且迁移收益超过成本 | 业务和存储适配、数据迁移、运维重新评估 |

uni-app 不强制搭配 uniCloud。CloudBase 自定义登录 Ticket 是候选鉴权方案，只有确认目标环境、SDK 和各端适配后才使用；默认公共接口采用平台无关的 HTTPS + 服务端会话设计，不依赖每端都能直接调用数据库 SDK。

### 5.2 登录、身份和权限

建议新增：

| 模型 | 关键字段 | 约束 |
| --- | --- | --- |
| users | userId、资料、封禁状态、时间 | 业务身份稳定，不因换平台而变化 |
| identities | provider、appId、subject、userId | provider + appId + subject 唯一；subject 来自平台服务端校验 |
| sessions | userId、身份来源、有效期、撤销状态 | access token 短有效期，refresh token 轮换并可撤销 |
| bindings | 绑定申请、确认双方、有效期、结果 | 一次性凭证，不能仅凭昵称头像认领 |

登录流程：客户端获取对应平台 code → 统一登录接口 → 后端用该平台密钥校验 code → 查找/创建 identity → 返回业务会话。QQ 若使用微信兼容宿主，按官方实际认证链路确定 provider，不预设必须 qq.login。

服务端验证签名/会话、过期、受众和撤销状态，再生成可信 actor。业务函数接收 actor.userId，不读取客户端传入的 openid、userId、isAdmin。HTTP 请求无微信上下文，不能从缺失或残留的进程环境推断身份。平台密钥只在服务端和 CI 对应秘密存储中维护。

旧微信云调用继续以可信 getWXContext 身份查映射，再调用同一业务层；HTTP 调用通过统一令牌获得同类 actor。两入口必须执行同一份密码、封禁、车头和管理鉴权。

初版允许每个平台独立注册业务用户；需要认领已有微信资产时，提供已登录账号发起、另一端确认的一次性绑定流程，或经验证的账号恢复方案。手机号并非所有平台都可用，不作为唯一前提。首版不自动合并两个已有资产账号；保留冲突处理流程，避免两边在同一队伍重复占位、封禁被合并绕过或管理角色意外转移。

### 5.3 API 设计草案

以下路径为拟议契约，实施前形成 OpenAPI 或等价 DTO 文档。

| API | 功能 | 权限/兼容要求 |
| --- | --- | --- |
| POST /v1/auth/login | 按 provider + appId 校验 code | 平台参数白名单，防重放与登录限流 |
| POST /v1/auth/refresh、/logout | 续期和撤销会话 | 轮换、登出与失效令牌验证 |
| GET/PATCH /v1/me | 读取/修改资料 | 封禁规则、资料校验、头像归属验证 |
| GET /v1/teams、/v1/teams/:id | 大厅和详情 | 原排序/分页语义，身份相关字段裁剪 |
| POST /v1/teams | 发车 | 原必填校验、限流、检测、事务 |
| PATCH /v1/teams/:id | 编辑 | 仅车头或明确授权角色 |
| POST /v1/teams/:id/join、/leave、/cancel | 加入、退出、取消 | 并发保护、重复操作幂等、原权限 |
| POST /v1/uploads | 获取受限上传凭证/执行上传 | 大小类型限制、归属和检测 |
| POST /v1/feedback、/bugs、/reports | 反馈/报错/举报 | 去重、限流、内容检测 |
| /v1/admin/*、/v1/organizer/* | 管理和代开 | 服务端角色校验，操作留痕 |

错误结构统一包含 code、message、requestId；兼容原 ok/errMsg/code 的旧客户端响应。业务码保留 NEED_PROFILE、BANNED 等语义，并定义 UNAUTHENTICATED、FORBIDDEN、TEAM_FULL、TEAM_EXPIRED、RATE_LIMITED、CONTENT_REJECTED。请求重试只对明确幂等的操作自动进行。

新建公开读取模式不是本次默认范围：当前云入口先取身份，迁移不能顺便放开匿名接口；若后续开放匿名浏览，单独列字段和权限契约。

### 5.4 存储、内容检测与通知

- 上传由统一服务授予有限权限；校验文件所有者、大小、类型和检测状态。头像被引用前完成检查，不接受任意用户 fileID 代替归属证明。
- 返回各端可读取的 HTTPS 图片地址；私有文件使用短期地址及刷新机制，不在数据库永久存储临时链接。
- 文本与图片检测做成服务模块。非微信内容不能伪造微信 OpenID 调用检测；选择可覆盖该来源的服务或平台能力。
- 记录当前检测接口异常时的放行行为，新增外部入口前明确异常处理、人工复核和监控方案；禁止以“接口不兼容”为由静默取消检测。
- 通知按 userId + platform identity + teamId + notificationType 管理投递和授权。绑定账户多端都有授权时，默认选可用的来源渠道，避免无意重复通知。
- 微信仍保持每局最多一条、提前开打提醒/散局通知共享额度的约定。其他端没有相应能力时明确提示，不承诺已设置提醒。
- 定时任务保留内部专用触发与鉴权；HTTP 客户端传 TriggerName/Type 不能执行提醒扫描。发送记录需防并发与重复投递，重试终态继续区分。

## 6. 数据迁移、兼容与回退

采用增量迁移，避免一次性替换所有 OpenID 和用户文档 ID。

1. 盘点并备份八个集合、存储对象、索引、权限规则、环境变量与触发器配置；在测试环境做恢复演练。
2. 从可信历史记录生成微信 identity → userId 映射，保存迁移批次、旧键和结果。脚本先 dry-run，按批可重入，冲突进入人工清单。
3. users 可暂保留旧文档 ID，新增 userId/映射索引；不直接改写文档主键。新非微信用户使用独立文档键并通过 repository 屏蔽差异。
4. teams 增加 ownerUserId，members 增加 userId，反馈/举报/审计增加 actorUserId。业务平台字段 Steam/手游/端游/主机保持原含义，另增 sourcePlatform/sourceAppId 表示应用来源。
5. 新字段存在时以新字段为准；只有缺失时才回退到已验证的旧微信映射。两者冲突必须告警并拒绝敏感写入，不能使用“任一匹配即放行”。
6. 双入口所有新写入统一产生业务身份；微信用户继续保留旧入口所需字段。跨平台用户不能用虚构微信 OpenID 填旧字段，也不能被旧微信通知器错误发送。
7. admins、organizers 和环境变量名单映射到业务角色；逐人核对、保持来源，不自动扩大权限。封禁、限流、举报去重也统一按业务用户执行。
8. 比对用户、队伍、成员计数、owner、密码访问、提醒结果和历史分享；仅在核对通过后切换主要读路径。
9. 兼容窗口内不删旧字段；待所有仍在线客户端与旧入口被验证兼容后，另开清理任务。

切换期间不维护两份独立生产数据库。若必须迁环境，先制定短停写/增量同步方案，明确源、目标、切换时间、校验和恢复方法，再执行。迁移期间新增写入必须可追踪，不能回退到过时快照而丢失新队伍。

回退重点：新版 UI 异常可恢复旧微信产物；新后端异常使用保留的兼容入口和功能开关；新平台停止新增写入时仍保留其已有用户和数据。撤回小程序包无法撤回已经写入数据库的数据，不能把前端回滚当成数据回滚。

## 7. 统一构建、上传和发布管理

### 7.1 配置与产物

建立每个平台的 appId、构建目标、包目录、能力开关、域名、上传适配和审核资料清单。配置中只存秘密引用，不写密钥。开发、测试、生产环境明确隔离。

一份源码版本允许多个端处于不同审核状态。发布记录至少包括 releaseId、Git SHA、业务版本、平台版本、artifact hash、API 契约版本、构建时间、上传结果、体验入口、提审状态、驳回原因、实际上线时间与回退版本。具体平台版本格式由各上传适配处理。

### 7.2 流水线

```text
人工触发候选版本 / Git tag
  → 安装锁定依赖、类型与静态检查、业务回归
  → 按已启用平台分别构建并保存不可变产物
  → 测试环境验证、生成体验入口
  → 按平台凭据上传，逐端记录成功/失败
  → 各端提审（支持且有权限的接口自动化，否则后台操作）
  → 审核状态汇总
  → 各端实际发布与线上验证
```

- 微信使用官方 miniprogram-ci；配置上传私钥和平台要求的 IP 策略。动态 runner IP 与白名单冲突时，评估固定出口 runner，不能默认取消 IP 限制。
- uni-mini-ci 可评估用于微信/企业微信、支付宝、钉钉上传，其文档未列出的端不默认支持。其他端对接官方可用 CLI/接口。
- QQ 的上传路径必须在路线确定后填写；复用微信包时增加 QQ 宿主验收步骤，而不是重复上传。
- 普通开发者上传能力和服务商代开发/提审权限分别验证。不能将服务商专用 API 作为个人账号已具备的能力。
- 每个平台单独 job，单端失败可只重试该端；同一平台同一版本避免并发覆盖。提审使用已验证产物，不临时重新构建。
- 上传日志不输出密钥和令牌，体验二维码等可能带访问能力的产物设定保留期和访问范围。
- 首期自动化目标是检查、构建、上传、结果汇总；提审和正式发布先保留独立操作，按实际 API 权限逐步自动化。

### 7.3 版本兼容

后端先部署向后兼容的新增接口/字段，再上传客户端。至少维护迁移期间仍在线的旧微信客户端和已上线各端所需契约；具体支持范围写入发布台账。不能因为某端审核通过就删除其他端仍需的字段。

“构建成功”“上传成功”“提审成功”“审核通过”“已发布”“真机线上可用”分别记录。不存在一处上传后所有平台立即同步上线的承诺。

## 8. 分阶段工作包与退出条件

以下工期为单人有效工程日的粗估，包含实现与工程验证，不包含平台审核、资格申请、域名准备及用户资料等待。每阶段结束根据证据重估，不能当作交付承诺。

| 阶段 | 粗估 | 交付物 | 退出条件 |
| --- | --- | --- | --- |
| P0 事实与接入验证 | 2–4 日 | 平台矩阵、云环境记录、QQ 路线原型、费用清单 | 第二宿主/平台能真实登录并授权访问测试数据，或明确外部阻塞与替代目标 |
| P1 工程和契约 | 2–3 日 | 新前端骨架、版本锁定、平台 adapter、API/actor 设计 | 微信及首个可接入端完成核心组件真机验证 |
| P2 统一身份和 API | 4–7 日 | 登录、会话、权限、HTTP/旧云双入口、上传检测接入 | 旧微信与新端访问同一测试大厅，越权与凭证用例通过 |
| P3 页面迁移 | 5–8 日 | 10 个页面与主要组件迁移、平台能力差异 | 两端完成发车/上车/下车/取消/反馈/管理闭环，微信旧分享可达 |
| P4 数据演练 | 2–4 日 | dry-run、回填/核对脚本、备份恢复及切换记录 | 测试快照无资产丢失、角色错配或密码越权，回退演练通过 |
| P5 CI 与首批上线 | 2–4 日 | 平台流水线、版本台账、发布/回退手册 | 可分别上传、重试和追踪；实际发布后完成线上验证 |
| P6 扩平台 | 每端初估 1–3 日 | 新端适配、资料和验收记录 | 准入满足、核心闭环及所用组件真机通过 |

P0–P5 顺序估算约 17–30 个有效工程日；如需迁移云环境、改造内容检测或处理复杂账号冲突，应另行估算。扩展端的复杂能力、平台审核不包含在“每端 1–3 日”内。

建议拆分成可审查提交：接入记录 → 工程骨架 → DTO/身份模型 → 登录和旧入口兼容 → 队伍 API → 上传/检测/通知 → 页面批次 → 迁移脚本 → CI → 发布记录。每次提交说明验证层级，不把线上验收混入静态检查结果。

## 9. 验证矩阵与验收标准

| 验证层 | 用例 | 通过证据 |
| --- | --- | --- |
| 原业务回归 | 现有 node 测试；补充统一 actor/映射/会话用例 | 测试输出和覆盖的业务行为清单 |
| 权限 | 访客、成员、车头、组局员、管理员、封禁用户 | 真接口响应与字段核对 |
| 密码 | 未加入不返回 roomPwd；授权成员范围与当前业务约定一致 | 双端响应不泄漏，hasPwd 可保留提示 |
| 并发 | 多端争最后一位、重复加入、重复提交发车、退出重试 | 不超员、不重复占位，成员与人数一致 |
| 身份 | 相同昵称不同人、伪造 userId、过期/撤销令牌、绑定冲突 | 无认领越权或封禁绕过 |
| 旧兼容 | 旧微信客户端、新微信客户端、其他端混合操作同队伍 | 资产归属、人数、编辑和旧分享一致 |
| 媒体 | 双端查看头像、上传拒绝、临时 URL 过期刷新 | 他人头像可读，私有原文件访问受控 |
| 检测通知 | 文本/图片拒绝和异常、无额度、定时重试、HTTP 伪造定时字段 | 不误发、不越权、不静默失去检测 |
| UI | iOS/Android 真机、长文本、键盘、低高度屏、加载失败 | 截图与操作记录，无遮挡、无不可点击入口 |
| 发布 | 单端上传失败、重试、审核版本错位、回退 | 平台级状态和产物可追溯 |
| 线上 | 正式账号登录、发车、跨端加入、权限、提醒 | 真实环境观察记录，不能用编译结果替代 |

现有测试只覆盖部分逻辑，不等价于真实平台授权、云数据库写入和线上发布验证。只为新增重要契约补测试，不为目录移动或文档内容编写镜像测试。

## 10. 风险、成本与观测

| 风险 | 处理与触发条件 |
| --- | --- |
| QQ 准入/能力不满足 | P0 提前查证；调整接入路线或暂缓该宿主，保留其他端工作 |
| UI 插件支持少于 uni-app | 首期组件原型验证，关键组件可用基础组件替代 |
| 旧身份错误迁移 | dry-run、唯一映射、分批核对、冲突不自动认领 |
| HTTP 暴露原内部操作 | 独立公开路由白名单，定时/管理/内部操作逐项鉴权 |
| 多端并发与重复提交 | 数据库事务、业务幂等键、唯一性约束或等价机制 |
| 平台审核错位 | API 向后兼容、独立发布状态、按平台能力开关 |
| 外部请求放大成本 | 网关/IP/账号分层限流，记录按平台的请求与错误量 |
| 多环境重复提醒/邮件 | 测试通知隔离，生产定时器只有受控实例运行 |
| 迁环境期间丢写入 | 单一写入源、增量追踪或明确停写窗口，恢复演练 |

成本在 P0 形成清单，不填未经核实的单价：云函数/云托管计算、数据库读写与索引、存储与出网、内容检测、短信（若启用）、域名和 HTTPS、CI 固定出口与执行时长。按测试/生产分别估算基础用量和增长后的用量。

关键观测字段：requestId、releaseId、平台、宿主、API 版本、耗时、业务错误码；必要身份使用内部 ID 或脱敏标识，不记录完整 token、密码和登录 code。优先观察登录失败、发车成功率、加入失败、权限拒绝、通知失败、迁移冲突和云费用变化。P0 记录现状，首批上线前据实际基线设定可执行的告警与回退阈值。
