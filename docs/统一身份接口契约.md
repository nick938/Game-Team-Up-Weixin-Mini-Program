# 统一身份接口契约（第一步，本地实现）

2026-10-15：HTTP 传输探测已通过，开始后端身份边界实现。本文及 `cloudfunctions/team/lib/identity.js` 尚未接入现有 team 入口、尚未部署生产身份逻辑，不代表微信或 QQ 已完成统一登录。

## 已实现的边界

- 内部 userId 规划为 `u_` 加 32 位小写十六进制 UUID 内容，由服务端生成并持久化。它不等于 OpenID，也不通过昵称或头像推断。
- 登录身份键为 SHA-256(JSON([provider, appId, subject]))，带 `identity_v1_` 前缀。三项共同隔离平台与应用；这是索引键，不是可用于登录的凭据。
- 微信 resolver 仅调用服务端注入的 `getTrustedContext()`，读取可信 APPID/OPENID，并校验预配置 AppID。它不接收请求 body/query/headers 作为身份来源。
- 按身份键查找记录，记录的身份三元组与键必须同时匹配；缺失时返回 IDENTITY_NOT_LINKED，冲突时返回 IDENTITY_CONFLICT，不自动创建、认领或回填生产数据。
- 输出内部 actor 只含 userId、provider、appId、legacyOpenId。管理员、组局员和封禁仍由业务权限服务核验；不复制映射中的角色信息。
- legacyOpenId 仅用于旧微信数据兼容，不能直接把内部 actor 返回前端；跨端统一鉴权尚需独立会话方案。

## 接入方式草案

```js
const resolver = createWechatIdentityResolver({
  getTrustedContext: () => cloud.getWXContext(),
  expectedAppId: configuredWechatAppId,
  findIdentity: key => identityRepository.findByKey(key),
});
const actor = await resolver.currentActor();
```

以上是接入示例，当前没有改动 team/index.js，也没有创建 identities 集合。

## 下一步实现顺序

1. 建立 identities repository 与对应唯一键/事务策略，在隔离测试数据上实现首次关联。已有微信用户须先验证旧用户文档归属，不能跳过历史资产映射。
2. 先为微信云入口提供兼容 adapter，将可信 OpenID 映射为业务 userId；旧读写路径保持可用并验证车头、成员、管理员和封禁行为。
3. 选择服务端持久化会话或经过验证的签名令牌方案，再实现 HTTP 登录与刷新、退出、撤销；不把身份哈希当 token。
4. 微信 HTTP code 登录必须后端向微信校验，密钥仅服务端配置；不能接受前端自报 OpenID。实际联调需要测试应用、域名与隔离数据准备。
5. QQ、抖音、支付宝只在各自适配器取得可信平台身份后复用映射规则；目前 provider 常量支持索引命名，不代表这些平台的认证适配已实现。

当前没有新增身份相关公网路由，没有生成/保存签名私钥，没有改动生产用户或队伍。真实登录、会话鉴权与业务闭环仍属于未完成工作。
