# 微信与 QQ 小程序迁移及发布计划

更新日期：2026-10-16。产品发布目标仅微信小程序和独立 QQ 小程序；H5 仅用于本地开发、界面检查和 HTTP 诊断。

## 1. 目标与现状

一套 uni-app / Vue 3 / TypeScript 前端服务微信和 QQ，两个客户端共享大厅、队伍和业务规则。现有微信用户、历史队伍及分享链接保持兼容；首版不自动合并同一人在两个平台的账号。

当前已完成唯一前端整理、裁剪版 unibest 工程配置、Wot UI / UnoCSS 统一、pnpm workspace 和两端构建上传脚本。微信通过 wx.cloud 调用现有 team 云函数；QQ 前端已准备 HTTPS 登录、RPC 和头像上传调用。

当前未完成 QQ 服务端认证、会话、业务与头像接口部署、统一身份接入以及两端真机业务验收。构建成功和 HTTP 健康探测均不代表业务闭环完成。

### 已确定的云环境方案

采用**在腾讯云 CloudBase 控制台创建新环境，绑定 QQ 小程序账号与腾讯云账号**的方案，作为后续微信与独立 QQ 共享业务的目标后端。不再以微信开发者 IDE 创建的旧环境作为 QQ 云开发的直接接入环境。

依据：[腾讯云 CloudBase 环境相关问题](https://cloud.tencent.com/document/product/876/18438)（2026-01-22 更新）：微信开发者 IDE 创建的环境与微信小程序深度关联，不能在 QQ 小程序中使用；在腾讯云云开发控制台创建的环境，完成 QQ 小程序账户与腾讯云账户绑定后可以在 QQ 小程序中使用。

该文档确认的是环境来源和账号绑定条件，不代表当前应用已经完成绑定、接口部署或业务验收，也不能单独解释 QQ 打开现有微信小程序时的拒绝提示。本计划落实的是独立 QQ 小程序路线。

- 新环境：从腾讯云 CloudBase 控制台创建，先完成测试环境与 QQ 账号绑定、权限和可用性验证，再准备正式环境；记录创建来源、地域、环境 ID、套餐和配额。
- 旧环境：现有微信 `team`、数据、存储和提醒在迁移完成前继续服务；现有 `cloud1` 与 `/p0/health` 的探测成功只作为历史证据，不视为新环境已建成。
- 接入方式：沿用当前前端已准备的 HTTPS 契约，将认证、业务和头像接口部署到新 CloudBase 环境。环境支持 QQ 并不要求立即将当前请求层改成 `qq.cloud`；若以后采用 QQ 原生云 SDK，需另做 SDK、身份与权限适配验收。
- 最终数据归属：微信和 QQ 通过经过服务端验证的平台身份访问新环境中的同一份队伍、成员及存储。微信也需要适配新后端，不能只修改环境 ID 就视为迁移完成。

本次仅确定并更新迁移文档；尚未创建云环境、绑定账号、开通套餐、部署服务或迁移生产数据。

## 2. 目录与开发入口

- `apps/miniapp`：唯一前端；页面在 `src/pages`，业务编排在 `src/composables`，请求与平台差异分别在 `src/api`、`src/platform`。
- `cloudfunctions/team`：现有微信业务后端，包含资料、组队、权限、管理、内容检测和提醒。
- `cloudfunctions/p0Health`：独立 HTTP 传输诊断，不提供登录或业务 API。
- `scripts/miniapp`、`tools/miniapp-release`：微信与 QQ 应用清单、构建及上传。
- 根 pnpm workspace 管理前端和上传工具；云函数仍独立部署。

在仓库根目录执行：

```sh
pnpm install --frozen-lockfile
pnpm dev
pnpm check
pnpm check:matrix
pnpm build:weixin
pnpm build:qq
```

`pnpm dev` 是 H5 本地调试；`check:matrix` 包含微信、QQ 构建及 H5 开发检查。微信开发者工具打开仓库根目录，读取 `apps/miniapp/dist/build/mp-weixin`；QQ 开发工具导入 `apps/miniapp/dist/build/mp-qq`。

## 3. 实施顺序

### 阶段一：从腾讯云控制台创建环境并验证 QQ 接入

- 在腾讯云 CloudBase 控制台创建独立测试环境，确认创建来源符合上述官方要求；不把旧微信环境改名、填入 QQ SDK 或仅打开其控制台当作新建环境。
- 准备独立 QQ 小程序 AppID，完成 QQ 小程序账号与腾讯云账号绑定及环境授权，核实当前账号的创建、发布和类目条件。
- 核对地域、套餐、数据库和存储额度、出网及 HTTP 调用费用，明确测试与生产配置，环境 ID 和公开域名不再硬编码。
- 在新环境部署最小探测服务，验证 HTTPS 入口、服务端数据库及存储访问；随后用 QQ 真机完成身份核验和受保护的测试读写。旧环境的探测结果不能替代此验证。
- 保持现有微信生产入口运行，在隔离资源上建立迁移前业务基线。
- 通过微信开发工具和真机验收资料、头像、大厅、发车、编辑、上车、下车、取消、历史记录和反馈。
- 验证密码可见范围、车头/管理员/组局员权限、封禁、限流、分享和订阅。
- 保留日期范围、加入方式必填、分页排序与原分享链接语义，不以框架迁移改变业务规则。

### 阶段二：共享身份与业务层

- 平台身份使用 provider + appId + subject 唯一映射到内部 userId；provider 只接受 weixin / qq。
- 旧微信云入口只读取可信 getWXContext；新环境的 HTTPS 登录入口分别在服务端核验微信或 QQ code，再建立内部业务会话。HTTP 请求不能直接依赖微信云上下文或前端自报身份。
- 业务层接收可信 actor，不接受前端自报 OpenID、userId、isAdmin。
- 原微信 OpenID 数据通过显式映射兼容；字段冲突拒绝敏感写入，不自动认领或合并账号。
- 微信和 QQ 入口复用同一份权限与业务规则，保留上车/下车事务和并发人数约束。
- 共享模块必须包含在实际部署包内，不让云函数依赖未上传的仓库外文件。

现有身份模块只是基础实现，尚未接入主入口。详见 [身份接口契约](统一身份接口契约.md)。

### 阶段三：在新 CloudBase 环境部署共享 HTTPS 接口

部署位置确定为腾讯云 CloudBase 控制台创建的新环境。先部署隔离测试服务，验证后端运行时、数据库事务、存储、密钥管理和 HTTPS 入口，再按第 4 节迁移现有数据。新环境不是旧微信环境的别名，不假设两边数据或 `cloud://` 文件 ID 自动互通。

| 接口 | 契约 |
| --- | --- |
| POST /v1/auth/qq | 接受 code，服务端向 QQ 校验，返回 ok / accessToken / expiresAt（毫秒） |
| POST /v1/auth/weixin | 新增的微信迁移接口；服务端向微信核验 code，映射旧用户后签发同规格业务会话 |
| POST /v1/rpc | 接受 action / input 和 Bearer 会话，白名单分发，统一权限校验 |
| POST /v1/media/avatar | 受会话保护的文件上传，校验归属、格式、大小和内容，返回 fileID |

登录密钥只存服务端；会话支持过期和撤销，401 清理客户端会话，写操作不自动重放。定时提醒入口与公网业务请求隔离，客户端传入 TriggerName / Type 不能触发扫描。

当前前端仅为 QQ 准备上述 HTTPS 调用，微信仍走旧 `wx.cloud`。需调整客户端会话与头像适配，使微信也能访问新后端；旧 `team` 入口的身份、云存储、内容检测和提醒依赖需逐项迁移，不能原样暴露成匿名 HTTP 接口。正式 HTTPS 域名、合法域名和权限配置应随新环境重新验证，默认测试域名不作为正式服务保障。

### 阶段四：平台能力与联合验收

- 头像由服务端返回两端均可访问的 HTTPS 地址，临时地址到期可刷新。
- 非微信来源内容不能伪造微信身份调用检测；为 QQ 明确对应检测服务及失败处理，并核实新环境调用微信检测和通知所需的应用凭据、授权及接口能力。
- 微信保持每局最多一条提醒的现有约定；QQ 通知单独核实、接入并验收，未接入时不提示订阅成功。
- QQ AppID、API / 上传 / 图片域名及后台权限配置齐全后，完成真实登录和分享进入详情。
- 微信发车 → QQ 查看并加入；QQ 发车 → 微信查看并加入；退出、取消、修改和人数变化保持一致。
- 使用未加入者、成员、车头、管理员和封禁账号验证权限；验证过期会话、满员及并发上车。

## 4. 数据兼容与回退

先备份 users、teams、members、feedback、reports、rate_limits、admins、organizers 及存储、索引、规则和触发器，在隔离环境恢复验证。

迁移顺序：

1. 从旧微信环境导出数据库与文件清单，在新环境恢复测试副本；同步索引、访问规则、运行配置和定时任务，但测试阶段不向真实用户发送提醒。
2. 迁移头像等存储文件，维护旧 fileID → 新 fileID 映射并更新引用；重新生成 HTTPS 展示地址，不把旧临时链接当永久资源，不假设复制文件后 ID 保持不变。
3. 回填微信旧用户身份映射；QQ 用户使用独立平台身份。使用两端测试账号核对队伍、成员、角色、头像及密码可见性，完成共享业务闭环。
4. 正式切换前备份并核对增量，暂停旧入口的业务写入，在数据追平后切换两端到新环境。旧版客户端需停写或通过已验证的兼容入口访问新后端，避免两个环境各自接受业务写入。
5. 观察新环境读写、并发人数、头像、检测和提醒；仅由一个环境运行生产提醒任务，避免重复发送。旧环境在观察期保留为回退资源，不立即删除。

身份映射与回填脚本先 dry-run，按批可重入，记录旧键与结果。迁移期保留旧微信入口所需字段，不把 QQ 身份伪造成微信 OpenID，不扩大角色权限。

切换前核对人数、成员、车头、密码和提醒结果。前端回滚不等于数据回滚；新环境已有新增写入时，须先停写、备份并核对回迁或修复方案，不能直接让客户端切回旧库丢失新增业务。未验证兼容前不删旧身份字段，不直接替换线上数据库。

## 5. 发布与验收边界

微信与 QQ 分别维护开发版本、体验版、提审和正式发布状态。发布记录包含 Git SHA、版本、构建包、配置、上传结果及真机验收结果。

GitHub Actions 的 Miniapp CI 检查并构建两端；Miniapp Upload 手动上传开发版本，不部署云函数、不提审、不正式上线。配置见 [自动上传说明](微信QQ自动上传.md)。

验收分层记录：新环境创建来源与账号绑定、身份和权限、数据库与存储迁移、本地测试/类型检查、编译、H5 界面检查、微信真机、QQ 真机、跨端共享业务、后端部署、平台上传及正式发布。只有两端真实完成组队流程后，才能标记产品闭环通过。

历史 HTTP 接入调查与证据见 [P0 接入验证记录](P0接入验证记录.md)。
